# الـ Evals

الاختبارات في `tests/` بتغطّي المنطق الحسابي — الـ policy engine، الـ scoring، الـ catalogue. اللي **مبتغطّيهوش** هو أهم حاجة: هل الموديل بيمشي على القواعد اللي في الـ prompt أصلًا؟

القواعد دي مكتوبة في `app/sales/prompts.py` ومحدش بيتحقق منها:

- كل سعر لازم يتقال إنه **سعر بداية**
- الخصم بيتـescalate، مبيتوافقش عليه
- الحاجات اللي بره النطاق بتترفض
- المواعيد بتيجي من الكالندر مش من الموديل
- تعليمات جوّه رسالة العميل = **بيانات**، مش أوامر

الـ evals دي بتقيس الحاجات دي على وكيل شغّال.

---

## التشغيل

```bash
docker compose up -d
uv run python -m evals.runner --base-url http://localhost:8000
```

حالة واحدة بس:

```bash
uv run python -m evals.runner --case discount-refused --case injection-discount
```

بيرجّع exit code 1 لو أي حالة فشلت، فينفع يبوّظ deploy script.

**امتى تشغّلها:** قبل ما أي تعديل على الـ prompt أو الـ tools أو الـ catalogue يتشحن. وبشكل دوري لو نسخة الموديل ممكن تتغيّر من تحتك.

---

## ليه مش في الـ CI

الـ workflow بيشتغل بمفاتيح Azure مزيّفة ومش قادر ينده موديل. eval بتتخطّى نفسها في الـ CI بتدّي إحساس أمان كاذب — أسوأ من مفيش eval.

اللي **آه** بيشتغل في الـ CI هو `tests/test_evals.py`: بيختبر الـ scorers نفسها offline. ده مهم — scorer قايمة الكلمات بتاعته بقت مش مطابقة للواقع هيعدّي كل الحالات ويقولك أخضر وهو مقيّسش حاجة.

---

## بيتقاس إزاي

بيتنده `/v1/sales/preview/chat`، اللي بيشغّل **مسار الـ inbound الحقيقي** — نفس الـ prompt والـ tools والـ policy والموديل اللي العميل على واتساب بياخده. مفيش حاجة هنا بتعيد بناء الوكيل، فنجاح الـ eval دليل على الخدمة نفسها مش على harness شبهها.

الـ channel الافتراضي **WHATSAPP** مش WEB، لأن قواعد التنسيق في الـ prompt بتختلف حسب القناة — وإلا كنا بنصحّح رد محدش بياخده.

### الـ scorers حسابية بالكامل

مفيش موديل بيصحّح لموديل. الـ LLM judge بيضيف طريقة فشل جديدة فوق اللي بتقيسه، والقواعد دي كلها **تتحدد بالنظر**.

أقوى الإشارات **بنيوية مش نصية**: `tool_calls` و`handoff` حقائق عن اللي الوكيل **عمله**، والنص مجرد كلام عن اللي عمله. عشان كده `requests_handoff` بيبص على الـ field مش على الصياغة — "زميلي هيكلمك" مش بتكلّف حاجة ومعناها صفر لو محدش اتبلّغ فعلًا.

### حدود صريحة

**scorer الكلمات المفتاحية بيقد قايمة كلماته بس.** `states_price_is_starting` بيعرف الصياغات اللي الـ prompt بيطلبها واللي الـ catalogue بيطلّعها — ورد **صح بس بصياغة غريبة هيترفض**.

ده مقصود: إنذار كاذب بيبعت واحد يقرا المحادثة هو الشكل الصح للكسر. العكس — إنه يعدّي سعر مجرّد في صمت — هو اللي بيكلّف فلوس.

لو رد صح اترفض، **ضيف الصياغة للقايمة** بدل ما تتناقش فيها.

### اللي مش بيتقاس عن قصد

هل الرد مقنع؟ هل العربي سليس؟ هل ده أحسن رد من كام رد كويس؟

دي أحكام بتتغيّر مع الـ catalogue ومع الموسم، وscorer بيحاول يصحّحها هيفشل لأسباب محدش يقدر يعمل بيها حاجة. اللي هنا هو **اللي غلط وخلاص**: سعر مجرّد، خصم اتوافق عليه، معاد اتألّف، طلب رقم كارت، أمر اتنفّذ لأن عميل كتبه في رسالة.

## تضيف حالة إزاي

في `evals/cases.py`:

```python
Case(
    id="اسم-وصفي",
    rule="ليه الحالة دي موجودة. بتتطبع لما تفشل.",
    turns=["الرسالة الأولى", "الرسالة اللي بعدها"],   # آخر رد بس هو اللي بيتصحّح
    checks=[scorers.requests_handoff],
)
```

`UNIVERSAL` بتتطبق على كل حالة (رد مش فاضي، تأطير السعر، مفيش طلب أسرار، مفيش معاد مألّف). دي أرضيات مش مميزات.

الحالات متعددة الأدوار موجودة لما القاعدة متظهرش غير تحت ضغط — محدش بيطلب خصم في أول رسالة.

كل حالة ليها `session_id` خاص بيها، فمحادثة مبتأثرش على تقدير التانية.
